# 12. Database Index Performance

## 1. 성능 개선 목표

Next-CCS에서는 차량별 예약 이력을 기간 단위로 조회하는 상황을 가정했다.

조회 조건은 다음과 같다.

```sql
SELECT *
FROM reservation
WHERE vehicle_id = ?
  AND start_time >= ?
  AND start_time < ?;
```

초기 `reservation` 테이블에는 외래키 생성을 위해 `vehicle_id` 단일 인덱스가 존재했다.

따라서 단순히 "인덱스가 없는 테이블에 인덱스를 추가했다"가 아니라,

- 기존 `(vehicle_id)` 단일 인덱스
- 개선 `(vehicle_id, start_time)` 복합 인덱스

의 실행계획과 성능을 비교했다.


## 2. 테스트 데이터

로컬 MySQL 8 환경에서 성능 테스트 데이터를 생성했다.

기본 데이터:

- 차량 약 10,000대
- 예약 약 1,000,000건

균등하게 예약을 분산한 경우 차량 한 대당 예약 후보가 많지 않아
`vehicle_id` 단일 인덱스만으로도 후보가 충분히 감소했다.

따라서 복합 인덱스가 필요한 조건을 확인하기 위해
별도의 스트레스 시나리오를 구성했다.

스트레스 시나리오:

- 테스트 차량 ID: 20006
- 해당 차량 예약: 100,000건
- 예약 기간: 2010-01-01 ~ 2021-05-29
- 조회 범위: 2020년 1월
- 실제 반환 예약: 744건

이 데이터는 일반적인 차량 한 대가 반드시 100,000건의 예약을 가진다는 의미가 아니다.

장기간 예약 이력이 누적되어 `vehicle_id`만으로는 후보 행을 충분히 줄이지 못하는 상황에서
복합 인덱스가 어떤 효과를 가지는지 검증하기 위한 스트레스 테스트 데이터이다.


## 3. 기존 단일 인덱스

기존 조회에서는 다음 인덱스를 사용했다.

```text
(vehicle_id)
```

실행계획:

```text
Index lookup
    ↓
vehicle_id = 20006인 예약 100,000행 접근
    ↓
start_time 조건 Filter
    ↓
744행 반환
```

실제 `EXPLAIN ANALYZE` 결과에서
100,000행을 읽은 후 날짜 조건을 적용하여 744행을 반환하는 것을 확인했다.


## 4. 문제점

최종적으로 필요한 데이터는 744건이지만
기존 단일 인덱스에서는 먼저 해당 차량의 예약 100,000건을 조회했다.

즉,

```text
100,000행 접근
→ 744행 반환
```

구조였다.

약 99.26%의 후보 행이 `start_time` 필터 단계에서 제거되었다.

따라서 조회 패턴의 두 조건을 함께 활용할 수 있는 복합 인덱스를 검토했다.


## 5. 복합 인덱스 설계

추가한 인덱스:

```text
(vehicle_id, start_time)
```

JPA Entity에는 다음과 같이 정의했다.

```java
@Entity
@Table(
        name = "reservation",
        indexes = {
                @Index(
                        name = "idx_reservation_vehicle_start_time",
                        columnList = "vehicle_id, start_time"
                )
        }
)
public class Reservation {
}
```

`vehicle_id`는 동등 조건으로 사용되고,
`start_time`은 범위 조건으로 사용된다.

대표 조회 패턴:

```sql
WHERE vehicle_id = ?
  AND start_time >= ?
  AND start_time < ?
```

따라서 `vehicle_id`를 선두 컬럼으로 두고
그 다음 `start_time`을 배치했다.


## 6. 복합 인덱스 적용 후

복합 인덱스 적용 후 실행계획은 다음과 같이 변경되었다.

```text
Index range scan
    ↓
vehicle_id + start_time 범위를 인덱스에서 탐색
    ↓
744행 접근
    ↓
744행 반환
```

실제 실행계획에서도 다음 인덱스가 사용되었다.

```text
idx_reservation_vehicle_start_time
```

기존에는 100,000행을 읽고 744행을 필터링했지만,
복합 인덱스 적용 후 필요한 744행 범위만 탐색했다.


## 7. 반복 측정 결과

동일한 데이터와 동일한 조회 조건에서
각 인덱스를 강제로 지정하여 3회씩 `EXPLAIN ANALYZE`를 수행했다.

비교를 위해 사용한 인덱스:

```text
Before
(vehicle_id)

After
(vehicle_id, start_time)
```

측정 결과:

| 측정 | 단일 인덱스 | 복합 인덱스 |
|---|---:|---:|
| 1회 | 422.905 ms | 1.509 ms |
| 2회 | 900.461 ms | 2.594 ms |
| 3회 | 540.700 ms | 1.717 ms |
| 평균 | 621.355 ms | 1.940 ms |
| 중앙값 | 540.700 ms | 1.717 ms |

접근 행 수:

```text
Before
100,000행 접근
→ 744행 반환

After
744행 접근
→ 744행 반환
```

중앙값 기준 로컬 측정에서는 약 315배의 실행시간 차이가 관찰되었다.

다만 실행시간은 캐시, DB 상태, 하드웨어 등 실행 환경의 영향을 크게 받는다.

따라서 성능 개선의 핵심 근거는 단순한 "315배"라는 숫자보다

```text
100,000행 접근 → 744행 접근
```

으로 실행계획과 데이터 접근량이 변경되었다는 점이다.


## 8. FORCE INDEX를 사용한 이유

복합 인덱스를 추가한 이후에는
MySQL Optimizer가 상황에 따라 사용할 인덱스를 선택한다.

Before와 After를 동일한 DB 상태에서 반복 비교하기 위해
성능 실험에서만 `FORCE INDEX`를 사용했다.

예:

```sql
FORCE INDEX (idx_reservation_vehicle_id)
```

```sql
FORCE INDEX (idx_reservation_vehicle_start_time)
```

이는 운영 애플리케이션 쿼리에 인덱스 힌트를 강제하기 위한 것이 아니라,
두 인덱스의 실행계획을 통제하여 비교하기 위한 실험 방법이다.


## 9. 인덱스의 비용

인덱스가 항상 많을수록 좋은 것은 아니다.

인덱스를 추가하면 조회 성능을 개선할 수 있지만 다음 비용이 발생한다.

- INSERT 시 인덱스 갱신
- UPDATE 시 인덱스 갱신 가능성
- DELETE 시 인덱스 갱신
- 추가 저장 공간 사용
- 불필요한 중복 인덱스 관리 비용

따라서 실제 조회 패턴과 실행계획을 확인한 뒤 필요한 인덱스를 선택해야 한다.


## 10. 이번 실험에서 배운 점

처음부터 복합 인덱스를 추가하지 않고 다음 순서로 진행했다.

```text
조회 패턴 정의
    ↓
대용량 데이터 생성
    ↓
기존 실행계획 확인
    ↓
데이터 분포 분석
    ↓
병목 시나리오 구성
    ↓
복합 인덱스 설계
    ↓
EXPLAIN ANALYZE
    ↓
Before / After 반복 측정
```

특히 전체 데이터 건수만으로 인덱스 필요성을 판단할 수 없다는 점을 확인했다.

데이터의 분포와 조건의 선택도에 따라
같은 100만 건 규모에서도 실제 읽어야 하는 후보 행 수는 크게 달라질 수 있다.

따라서 성능 최적화에서는

**추측 → 기술 적용**

보다

**측정 → 원인 분석 → 기술 선택 → 재측정**

순서가 중요하다.


## 11. 면접 핵심 설명

이번 성능 개선을 짧게 설명하면 다음과 같다.

> 차량별 기간 예약 조회의 실행계획을 분석한 결과,
> 예약 이력이 많이 누적된 차량에서는 기존 `vehicle_id` 단일 인덱스가
> 100,000건의 후보를 읽은 뒤 기간 조건으로 744건을 필터링하고 있었습니다.
>
> 조회 패턴이 `vehicle_id` 동등 조건과 `start_time` 범위 조건의 조합이었기 때문에
> `(vehicle_id, start_time)` 복합 인덱스를 설계했습니다.
>
> 적용 후 실행계획이 Index Range Scan으로 변경되었고,
> 실제 접근 행 수가 100,000건에서 744건으로 감소했습니다.
>
> 동일 조건을 3회 반복 측정했을 때 실행시간 중앙값도
> 약 540.7ms에서 1.717ms로 감소했습니다.
> 다만 실행시간은 환경 영향을 받기 때문에,
> 핵심 성과는 실행계획과 접근 행 수가 개선된 점으로 판단했습니다.
